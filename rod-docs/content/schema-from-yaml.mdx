One of Rod's most powerful features is the ability to define schemas as data, not just as code. Rod can parse a YAML (or JSON) specification and build an executable validator tree at runtime. This is ideal for dynamic configuration, API contracts, form generation, or any scenario where validation rules are not known at compile time.

## Loading a Schema

The `from_yaml` function parses a YAML string conforming to the `RodSpec` format and returns a `Result` containing a fully functional `Box<dyn RodValidator>`.

```rust
use rod::{from_yaml, RodValidator};
use rod::io::json::wrap;
use serde_json::json;

let yaml_spec = r#"
type: object
properties:
  name:
    type: string
    min: 2
"#;

// Build the validator from the YAML string
let schema = from_yaml(yaml_spec).expect("Failed to parse YAML spec");

// Now, use the schema to validate data
let valid_data = json!({ "name": "Rod" });
assert!(schema.validate(&wrap(&valid_data)).is_ok());

let invalid_data = json!({ "name": "X" });
assert!(schema.validate(&wrap(&invalid_data)).is_err());
```

<Callout>
While this guide uses YAML for readability, the parser accepts any valid JSON or YAML, as it uses `serde_yaml`.
</Callout>

## The `RodSpec` Format

Every schema definition is an object with a `type` property that specifies the validator.

### `string`

Defines a string validator.

```yaml
type: string
min: 5          # Optional: minimum length
max: 100        # Optional: maximum length
length: 10      # Optional: exact length
email: true     # Optional: must be an email
url: true       # Optional: must be a URL
uuid: true      # Optional: must be a UUID
datetime: true  # Optional: must be an RFC 3339 datetime
ip: true        # Optional: must be an IP address (v4 or v6)
regex: "^[A-Z]" # Optional: must match this regex
starts_with: "prefix_" # Optional
ends_with: "_suffix"   # Optional
includes: "substring"  # Optional
trim: true      # Optional: trim whitespace before validating
```

### `number`

Defines a number validator.

```yaml
type: number
min: 0.0      # Optional: minimum value
max: 100.0    # Optional: maximum value
int: true     # Optional: must be an integer
```

### `boolean`

Defines a boolean validator. It has no additional properties.

```yaml
type: boolean
```

### `object`

Defines an object validator with a specific shape.

```yaml
type: object
# A map of property names to their RodSpec definitions.
properties:
  username:
    type: string
  age:
    type: number
    int: true
# Optional: Controls how to handle unknown keys.
# Can be 'true' for strict mode or 'false' (default) for strip mode.
strict: true 
```

| Property     | Type                              | Description                                                                                               |
|--------------|-----------------------------------|-----------------------------------------------------------------------------------------------------------|
| `type`       | `string` (must be `"object"`)     | Specifies the validator type.                                                                             |
| `properties` | `map<string, RodSpec>` (required) | A map where keys are property names and values are their corresponding schema definitions.                |
| `strict`     | `boolean` (optional)              | If `true`, validation fails on unrecognized keys. If `false` or omitted, unrecognized keys are stripped. |

### `array`

Defines an array where all elements must match a given schema.

```yaml
type: array
# The schema definition for each element in the array.
items:
  type: number
# Optional: Minimum number of elements.
min: 1
# Optional: Maximum number of elements.
max: 10
```

### `tuple`

Defines an array with a fixed number of elements, each with a potentially different type.

```yaml
type: tuple
# A list of schema definitions, one for each element in the tuple.
items:
  - type: string
  - type: number
  - type: boolean
```

### `union`

Defines a validator that accepts data matching any one of the provided schemas.

```yaml
type: union
# A list of possible schema definitions.
options:
  - type: string
  - type: number
```

### `literal`

Defines a validator that only accepts a single, specific literal value.

```yaml
type: literal
# The exact value to match. Can be any valid JSON type.
value: "admin" 
```

Example with a number:
```yaml
type: literal
value: 404
```

### `enum`

Defines a validator that accepts one of a predefined set of string values.

```yaml
type: enum
# A list of allowed string values.
values:
  - "pending"
  - "completed"
  - "failed"
```

### `record`

Defines a dictionary-like object with validated keys and values.

```yaml
type: record
# Schema for the object keys. Must resolve to a string.
key:
  type: string
  min: 2
# Schema for the object values.
value:
  type: boolean
```

### `date`

Defines a validator for RFC 3339 date strings with optional range checks.

```yaml
type: date
# Optional: Minimum date as a Unix timestamp in milliseconds.
min: 1609459200000 # (Jan 1, 2021)
# Optional: Maximum date as a Unix timestamp in milliseconds.
max: 1640995200000 # (Jan 1, 2022)
```

<Callout>
For more complex or unsupported validators like `lazy`, `map`, `set`, and `intersection`, you will need to construct them programmatically in Rust. The YAML format is designed to cover the most common use cases for data-driven validation.
</Callout>
