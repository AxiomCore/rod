# Performance Guide

Since Rod operates across language boundaries, how you use it matters more than with native libraries. Here are the best practices to minimize the "Bridge Tax."

## 1. Prefer `checkBatch` for Arrays

If you are filtering a large dataset (e.g., 100k rows) in JavaScript, do **not** use `.parse()` in a loop.

❌ **Slow (High Overhead)**
```typescript
const results = items.map(item => Schema.parse(item));
```

✅ **Fast (Low Overhead)**
```typescript
// Returns a Uint8Array bitmask (1=valid, 0=invalid)
const mask = Schema.checkBatch(items);

// Filter efficiently in JS
const validItems = items.filter((_, i) => mask[i] === 1);
```

This reduces 100,000 FFI calls down to **1 FFI call**.

## 2. Use Discriminated Unions

Always prefer `rod.discriminatedUnion` over `rod.union`.

- **Standard Union:** Rod tries every schema until one works. ($O(N)$)
- **Discriminated Union:** Rod checks one key and jumps to the correct validator. ($O(1)$)

## 3. Avoid Regex for Simple Checks

Rod currently compiles Regex patterns on-the-fly. This is expensive.
If you just need to check if a string starts with "http", use the native helper:

❌ **Slow**
```typescript
rod.string().regex("^http")
```

✅ **Fast**
```typescript
rod.string().startsWith("http")
```

## 4. JS Parsing Modes

- Use `mode: 'lazy'` (Default) for **Large Objects** where you check few fields. It avoids serializing the whole object.
- Use `mode: 'eager'` for **Massive Arrays of Primitives** (e.g., `number[]`). Serializing an array of numbers to JSON is fast, and validating them in Rust is instant.

```typescript
// For array of 100k numbers
NumberArray.parse(data, { mode: 'eager' });
```

## 5. When to stick with Zod/Pydantic

If your application:
- Is 100% JavaScript (Frontend only).
- Validates tiny objects (simple forms) at high frequency.
- Does not need to share logic with a Rust/Python backend.

...then stick with **Zod**. It is specialized for V8 and will always be faster for simple cases because it lives inside the engine.

Use **Rod** when **Consistency** across languages is more important than raw micro-benchmark speed.
